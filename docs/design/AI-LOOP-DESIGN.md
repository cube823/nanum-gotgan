# 나눔곳간 — AI 루프 설계 (부가 기능, MVP 범위 밖)

> **읽는 순서**: `MVP.md`(AI 없는 본체) → 그게 돌아간 뒤 이 문서.
>
> AI 토글 2개(`여러 물건 글쓰기` / `AI로 작성해요`)는 등록 화면의 **부가 기능**이다.
> 없어도 서비스는 돌아간다 — 사진 찍고 손으로 입력하면 등록이 된다.
> 구현체는 `ai/`에 있고, `MVP.md` §부록에 붙이는 방법이 있다.
>
> **아직 검증되지 않았다**: AI가 물품 사진을 제대로 분류하고 쓸 만한 한국어 설명을
> 쓰는지 실측하지 않았다. 골든셋 20장 필요 (`ai/README.md`).

## 1. AI가 실제로 필요한 지점은 하나다

등록 플로우를 보면 담당자가 겪는 실제 비용은 이것이다:

> 행사 끝나고 남은 잡동사니 20개를 사진 찍었다. 이걸 게시글 20개로 만들려면 각각 카테고리·물품명·수량·상태·설명을 손으로 입력해야 한다.

이 한 지점이 서비스 성패를 가른다. 등록이 귀찮으면 물건이 안 올라오고, 물건이 없으면 스와이프할 게 없다. **AI 루프는 여기 하나에만 건다.**

반대로 AI를 넣지 **않는** 곳:

- **매칭/추천** — 초기엔 아이템이 수십 개다. 정렬만으로 충분하다. 추천 모델은 데이터가 쌓인 뒤 이야기.
- **메시지 자동응답** — 기관 담당자 간 대화다. AI가 대신 쓰면 신뢰가 깨진다.
- **법적 판정** — 리스크 등급은 규칙표(§3)로 충분. LLM에게 법 판단을 위임하지 않는다.

## 2. AI 루프 (사진 N장 → 게시글 M개)

```
[1] 사진 N장 (최대 30)
      ↓
[2] GROUP     같은 물건끼리 묶기            → M개 그룹
      ↓
[3] EXTRACT   그룹별 구조화 필드 추출        → M개 draft (JSON)
      ↓
[4] GUARD     규칙 기반 검증 (LLM 아님)      → 등급 + 경고
      ↓
[5] REVIEW    사용자가 카드로 확인·수정      ← 사람이 반드시 통과
      ↓
[6] COMMIT    게시글 M개 등록
```

**루프인 이유**: [5]에서 사용자가 "이 두 개는 같은 물건이야" 하고 병합하거나 "설명 다시" 하면 해당 그룹만 [2]/[3]으로 되돌아간다. 전체 재실행 아님.

### 각 단계

**[2] GROUP** — Vision 모델 1콜. 사진 N장을 한 번에 넣고 그룹 인덱스만 받는다.
```json
{"groups": [{"photos": [0,1,2], "hint": "검정 유성펜 묶음"}, {"photos": [3], "hint": "크라프트 종이봉투"}]}
```
`AI로 작성해요`만 켜고 `여러 물건 글쓰기`가 꺼져 있으면 이 단계를 건너뛴다 (전부 한 그룹).

**[3] EXTRACT** — 그룹마다 1콜. 02·03 기획서의 카드 필드에 정확히 매핑한다:
```json
{
  "category": "문구·사무용품",     // 고정 enum (§3 표와 1:1)
  "name": "유성 매직 검정",
  "quantity": {"value": 10, "unit": "개"},
  "used": true,                    // 02: 사용 여부 yes/no
  "condition": "중",               // 02: 상·중·하
  "description": "행사 후 남아 양도합니다. 사용감 조금 있습니다.",
  "confidence": 0.0~1.0
}
```
`description` 톤은 02 기획서 예시문을 따른다 — "이 물품은 ~용도로 샀으나, 행사 이후 남아서 양도합니다."

**[4] GUARD** — **LLM을 쓰지 않는다.** category → 리스크 등급 매핑(§3)과 필수값 체크뿐. 결정적이어야 하고, 감사 대응 근거가 되어야 하므로.

**[5] REVIEW** — 생성 결과는 **초안일 뿐**. 03 기획서의 "n장 올리기" 버튼처럼 "M개 등록하기"로 넘어가되, 그 전에 카드 M장을 넘기며 확인한다. `confidence < 0.6` 필드는 미리 하이라이트해 시선을 유도한다.

## 3. 법적 가드레일 — 코드로 박는다

법적 검토 문서가 이미 판정을 끝냈다. LLM에게 다시 묻지 말고 테이블로 고정한다.

```
🟢 자유   문구·사무용품 / 포장·박스류 / 공예 재료 / 일회용품·위생용품 / 폐홍보물·인쇄물 / 폐현수막·배너
🟡 확인   행사·파티용품 / 인테리어·소품          → "반복 사용품이면 비품일 수 있어요" 안내
🔴 주의   전기·소형비품                          → 대장 등재 여부 입력 + 승인 확인 단계 강제
```

AI가 🔴로 분류하면 **자동 등록을 막고** 사람에게 넘긴다. 등급을 낮추는 방향의 AI 판단은 무시한다 (fail-safe는 항상 더 엄격한 쪽).

추가로 스키마에 고정 필드 (법적 검토 §5 체크리스트에서 그대로):
- `on_ledger`: 물품 대장 등재 여부
- `approval_confirmed`: (비품인 경우) 내부 처분 승인 여부
- `funding_source`: 취득 재원 (보조금 여부)
- `org_type`: 위탁 / 직영 — 가입 시 1회 입력, 직영 + 대장 등재 시에만 "물품관리관 결재 완료" 단계 추가

이 네 개는 **AI가 채우지 않는다.** 사진으로 알 수 없고, 틀리면 감사 이슈가 된다. 사람이 입력한다.

## 4. 모델 선택

| 단계 | 모델 | 근거 |
|---|---|---|
| GROUP | `claude-haiku-4-5` | 이미지 다수 입력, 출력은 인덱스 배열뿐. 싼 게 맞다 |
| EXTRACT | `claude-sonnet-5` | 한국어 설명문 품질이 곧 게시글 품질. 여기만 값을 쓴다 |
| GUARD | 없음 | 규칙 코드 |

두 단계 모두 **tool use / structured output으로 스키마 강제**한다. 자유 텍스트 파싱 금지.

30장 × 그룹 M개면 EXTRACT가 M콜이다. 그룹이 15개를 넘으면 사용자에게 "너무 많아요, 나눠서 올려주세요"로 끊는다 — 비용도 비용이지만 [5] REVIEW에서 사람이 15장 넘게 검토 못 한다.

## 5. 실패 처리

| 상황 | 처리 |
|---|---|
| GROUP 실패 | 전체 1그룹으로 폴백 → 사용자가 수동 분리 |
| EXTRACT 실패 (그룹 1개) | 그 그룹만 빈 폼으로 → 나머지 M-1개는 살린다 |
| 스키마 위반 | 1회 재시도 → 실패 시 빈 폼 |
| 타임아웃 | 부분 결과라도 REVIEW로 넘김 |

**AI 실패가 등록 자체를 막지 않는다.** 수동 등록 경로는 항상 열려 있다 — 03 기획서의 원래 플로우가 그것이다. AI는 어디까지나 가속기다.
